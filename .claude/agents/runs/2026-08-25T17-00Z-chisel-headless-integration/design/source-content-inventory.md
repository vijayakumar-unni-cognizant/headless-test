## 0. CRITICAL FIDELITY DISCLOSURE — read before treating this as byte-exact

### 0.1 What failed in r01

The r01 version of this document was built entirely from `WebFetch` (fetch → HTML-to-markdown → secondary-model extraction) and marked every one of its 94 items "verbatim" with a single blanket disclosure that the pipeline *might* normalize characters. That disclosure understated the actual failure mode. The Program Agent's `curl`-based spot-check (`DECISIONS.md 2026-08-26T09:00Z`) found that several r01 items were not character-level drift — they were **entire fabricated sentences in the source's voice**: a page title that does not exist anywhere in the raw HTML, a hero paragraph built from vocabulary that appears on the page but recombined into a sentence that was never written, page-metadata dates invented where the real page had none. Other items (the stat block, the closing tagline) were byte-exact. Nothing in the r01 document distinguished the two classes.

### 0.2 What I did differently this time

The Program Agent supplied raw HTTP response bodies for all 4 pages, fetched via `curl` (a tool I do not have) and staged at the local paths given in my dispatch prompt. For this correction pass I read those raw files directly using `Grep` (targeted patterns, bounded context windows to stay inside the tool's per-match length limit) and `Read` (only where I needed to see surrounding markup structure that `Grep` couldn't isolate). **No `WebFetch` call was made anywhere in this correction pass.**

For every one of the 94 items in this document, I searched the raw HTML for an exact substring match of the claimed value. Where I found one, I quote the surrounding markup as evidence and mark the item `verbatim (source-confirmed)`. Where I could not find a match, I did not invent a replacement — I report either (a) a different real string I *did* find nearby that appears to be the actual content for that region, which I substitute in with its own confirmation evidence, or (b) an explicit `UNCERTAIN — no exact match found in raw HTML` with a description of what, if anything, exists in that region instead.

I cross-checked using the redundancy the raw HTML actually offers: most body copy appears twice — once as plain HTML text between tags, once again inside the escaped RSC JSON payload (`\"children\":\"...\"` patterns) that Next.js embeds for client hydration. Where both forms agreed I treat that as strong confirmation. Structured metadata (`<title>`, `<meta name="description">`, `og:*`, `twitter:*`, `rel="canonical"`, and the JSON-LD `<script type="application/ld+json">` blocks for `Organization` / `WebPage` / `WebSite` / `VideoObject` / `Brand`) is also load-bearing evidence and is cited as such, distinct from "visible on-page prose" — I flag which is which per item, because a JSON-LD field is real, sourced content, but is not necessarily the string a human reader sees on the rendered page.

### 0.3 What this correction pass found, in aggregate

Of the **81 in-scope content items**, direct raw-HTML re-verification produced:
- **67 items fully `verbatim (source-confirmed)`** — either the r01 value was already correct (this was true for most short structured "card" copy: stat blocks, pillar/offering cards, role-roster short labels, product-by-trade taglines), or I replaced a fabricated r01 value with the real on-page string I located at that same content position.

These should be treated as **not backed by any source** unless a further, different fetch confirms them; **do not author them into a Content Fragment**.

This is a large improvement in confidence over r01, but it is **not a claim of perfect byte-fidelity**: `Grep`'s regex-based extraction can still miss HTML-entity-decoding edge cases (`&#x27;` vs. `'`, `&amp;` vs `&`) that I have transcribed by hand below — I decoded these by inspection, not by an automated decoder, and a mis-transcription at that level is possible even though the substance is confirmed.
